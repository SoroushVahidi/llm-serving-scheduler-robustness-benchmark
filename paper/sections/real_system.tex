\section{Real-System Validation}
\label{sec:real-system}

\subsection{Objective}
\label{sec:real-system-objective}

This analysis answers RQ6 (\S\ref{sec:rq}). We do not claim, here or
anywhere in this manuscript, that simulated absolute latency or throughput
values match real-hardware values; simulator latency is not assumed to
transfer to real-engine latency, and the simulator's own load-calibration
reference $\lambda_{\mathrm{ref}}$ (\S\ref{sec:calibration}) is not assumed
to transfer to a real engine's saturation point either. The only claim in
scope is agreement in \emph{relative ranking} and \emph{reversal
direction} between the simulator and a real vLLM deployment on a small,
frozen set of validation cases -- not a hardware duplication of the full
18{,}720-cell Pilot-V2 matrix
(\texttt{docs/REAL\_SYSTEM\_VALIDATION\_PLAN.md}).

\subsection{Planned Design}
\label{sec:real-system-design}

The following design is prepared and, at the engineering-infrastructure
level, partially exercised (\S\ref{sec:artifact}); it is not yet run as a
scientific validation, because case selection depends on
\S\ref{sec:cross-source-rankings}/\S\ref{sec:reversals}, which do not yet
exist.

\begin{itemize}
  \item \textbf{Mechanisms.} Approximately four representative
    scheduling mechanisms, one from each stratum in
    \S\ref{sec:fidelity} that has a real or faithfully reimplementable
    execution path on an actual serving engine -- e.g.\ \texttt{fifo},
    \texttt{vllm\_faithful} (or its chunked-prefill successor), and
    \texttt{sarathi\_faithful}, plus a fairness-aware mechanism where a
    real-engine analogue can be established;
    \texttt{apt\_serve\_faithful} is excluded, consistent with its
    \texttt{scaffolding\_only} status (\S\ref{sec:panel}).
  \item \textbf{Cases.} Three to four workload/case conditions, chosen to
    include at least one case exhibiting a preregistered
    \texttt{SUPPORTED\_PRACTICAL\_REVERSAL} (\S\ref{sec:uncertainty}) from
    the simulated analysis and at least one stable-ordering control
    condition -- selection frozen only from this study's own completed
    results, never from a partial or in-progress result.
  \item \textbf{Operating regions.} \texttt{PRE\_KNEE} and
    \texttt{KNEE}/\texttt{OVERLOAD}, recalibrated against the real
    engine's own observed saturation point rather than reusing the
    simulator's calibrated load factors (\S\ref{sec:calibration}) directly.
  \item \textbf{Repetitions.} At least five repetitions per
    (mechanism, case, region) cell, in contrast to the simulator's
    deterministic single execution plus rep0/rep1 verification
    (\S\ref{sec:paired}) -- real hardware execution is not deterministic,
    so repeated stochastic trials are required here even though they were
    not required in simulation.
  \item \textbf{Ordering.} Randomized or ABBA ordering of mechanism/cell
    execution, to avoid confounding a mechanism's measured performance
    with time-of-day GPU-sharing effects.
  \item \textbf{Manifests.} Fixed workload request manifests, generated
    once per case and reused verbatim across mechanisms and repetitions,
    with an explicit warmup phase discarded before measurement.
  \item \textbf{Provenance.} Every real-engine run records its exact
    hardware model, driver and CUDA version, Python/PyTorch/vLLM version,
    model identity and revision, scheduler configuration, workload-manifest
    hash, run-order seed, and repository commit SHA, so that any released
    real-validation row is independently reproducible
    (\S\ref{sec:artifact}).
\end{itemize}
