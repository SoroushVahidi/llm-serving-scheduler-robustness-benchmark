Use the existing GitHub repository, not a redundant repository. A release can be based on a later approved packaging commit without merging PRs #27–29; the commit/tag must be reviewed before publication, including GitHub's automatic whole-tree source downloads. This task prepares the compact source asset, not a public tag. Historical main and PRs are untouched.

Recommend a separate HF identity `SoroushVahidi/llm-serving-common-contract-m3`. Its four-policy CM-0.1 contract, statistical calibration and equivalence proof differ from the 13-policy Phase-12 LSSP dataset. A separate identity avoids silently changing the meaning of scheduler_outcomes or aggregating dependent experiments. Link to the older dataset as related input/history. Existing HF v1.1.0 and GitHub v1.0.0/v1.1.0 identities remain intact. Proposed Kaggle identity: `soroushvahidi/llm-serving-common-contract-m3`; its native initial version 1 maps explicitly to m3-v1.0.0. Neither proposed URL is live or reserved.

The complete archive is too large for a single GitHub release asset (each must be below 2 GiB: https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases). Store it once on Zenodo; use compact source and tables on GitHub. HF/Kaggle mirror only useful tables; they are access copies, not independent results. Verify every downloaded table against the shared table manifest after publication. Kaggle's flat files avoid directory-upload omission and unwanted table conversion. Actual account quotas and upload behavior must be rechecked at publication.

Create a **new related Zenodo record and new concept**, not a new version under the older software DOI. The old DOI 10.5281/zenodo.22306798 identifies the source-only LSSP v1.0.0 archive, with concept DOI 10.5281/zenodo.22306797. Use a related-reference relationship to that historical record and explicit component/supplement relationships to the eventually verified M3 GitHub, HF and Kaggle releases. Do not label a subset as isIdenticalTo the full artifact. Preserve the mixed license boundaries; the proposed metadata uses a custom component-license description instead of a blanket MIT claim. Do not trigger a second automatic GitHub-to-Zenodo deposit with indistinguishable M3 scope.

Only the versioned central repository/release and version-specific new Zenodo DOI should need direct manuscript links. HF and Kaggle can be linked through the central release and archival record, reducing manuscript length and maintenance burden. Citation metadata omits invented DOI, publication date, acceptance status and unverified ORCID.
