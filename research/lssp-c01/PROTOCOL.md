Ultimately, how many of the 36 historical reversal records persist? **This pilot cannot answer that second question.**

All six historical region factors (LOW, PRE_KNEE, KNEE, POST_KNEE, OVERLOAD, HIGH_PRESSURE); all four adaptations; two prespecified KV capacities. 3 × 6 × 4 × 2 = 144 cells. No replication of a deterministic cell. Window choice is independent of new outcomes; historical reversal evidence motivated the policy panel, so it is explicitly targeted and not a newly randomized sample. Low-load/source combinations and the sixth pair (Sarathi-inspired versus chunked FCFS) provide matched stable-ordering candidates; the manifest records historical labels rather than assuming every control is stable.

All five historical reversal pair families are represented by named adaptations. No claim of original-policy equivalence follows. An input or invariant failure stops the job; no failed cell is silently dropped, retried or replaced. One CPU Slurm job only, no arrays, no automatic Job 2. ## Contract CM-0.1: deliberately conservative resource model

* One abstract device, identical immutable configuration for every policy in each profile. This is a CPU discrete-event model, not a GPU measurement or native-engine emulation.
* Shared budget B=32,768 input/decode work tokens per 1 ms batch; max resident sequences=64. Every executed prompt token costs one budget unit; each selected decode request consumes one unit and produces one token. Step duration=0.001 s independent of batch composition, matching the historical time scale but not hardware cost. Report device busy seconds and token work separately; no physical GPU-cost claim.
* All policies may select any positive prefill chunk within the common budget and at most one decode token per request per batch. Policies decide ordering, chunk size and decode deferral; these are declared scheduling decisions. Engine executes the exact plan or rejects it, never substitutes a hidden plan.
* Shared context bound=32,768 tokens. All 24,000 frozen request lengths fit (max observed prompt+output=30,053). This bound was selected from input coverage before new outcomes; it is not an output predictor. **Every resident reserves the full 32,768-token context capacity**, independent of its latent output. Baseline KV capacity=131,072 tokens (four residents); sensitivity=262,144 tokens (eight residents). Actual used KV is computed from executed prompt/output prefix, rounded to 16-token blocks, and must remain within reservation. This conservative full-context reservation avoids prediction/oracle-based admission and memory deadlock, but strongly limits concurrency. It does not approximate native incremental allocation under pressure.
* No eviction, dropping, migration, prefix sharing or recomputation in this profile. Every policy has the same no-preemption action space. A waiting request owns no KV; a held resident retains its slot/reservation. Completion frees both. Reject out-of-domain inputs or actions; do not truncate prompts or outputs. General recomputation is a separate unvalidated contract.
* A prefill batch emits no output, including its final chunk. Decode begins no earlier than the next batch. This explicit synthetic convention differs from native final-prefill sampling, identically for all policies.
* Requests arriving during a batch become eligible at its end. Advance idle time directly to the next arrival. Common administrative horizon = last arrival + 50 s (the historical 50,000-step drain). No batch may finish beyond the horizon. Report all unfinished requests explicitly, never treat them as completed or as observed latencies.
* Policy view contains only arrived ID/stable ordinal, arrival, prompt length, acknowledged prefill/output progress, last output time, resident status and clock. No source identity, actual/remaining output, predicted output, future arrivals or output-derived deadline. Outputs live only in the execution/metric layer. Public IDs and immutable views are not a security sandbox; policy code is audited for permitted accesses.

## Input, metric and inference contract

Reuse full-window physical hash and historical campaign manifest pinned in REUSE_AND_GAPS. Synthesize and scale requests using unchanged historical code/seed/factor, retaining original request/source IDs and hashes. No future-output-derived prediction/deadline is passed to policy. Historical deadline remains in metric layer solely to make the historical ANWG definition comparable; its oracle-derived construction is disclosed. It is not a deployable SLO contract. No new synthetic tenant/class overlay.

Record per-request arrival, first output, completion, output tokens and unfinished state; exact intent/execution events; absolute mean/p95 completed latency, TTFT and TPOT (TPOT only output>1), completed count/fraction, output-token throughput, request throughput, busy-device seconds, prompt/decode work, and ANWG = sum priority of completed-in-deadline requests / sum priority of all arrivals. Missing metric values are null with counts. Throughput denominator is observed time from first arrival until final completion or administrative horizon if unfinished; also retain the denominator for interpretation.

Descriptive finite-corpus analysis only. No bootstrap, sign-test p-values, BH/FDR or nominal significance. Unit = whole window; no IID requests/regions/providers assumption. Pair metrics must use matched observed windows, with explicit missing counts. Ties use exact maxima and a relative1e-12 tolerance sensitivity; report sets, not forced IDs. The historical practical-margin screen is descriptive here: abs(a-b) / abs(losing value), opposite signs and strictly >0.10 on each side. A zero losing value is unestimable, not infinite evidence. A separately labeled alternative uses (a-b) / max(abs(a),abs(b),1e-12), opposite signs and >=0.10 on each side. Neither is a significance test. Record persistence/disappearance/emergence only where full historical support is present; otherwise `NOT_EVALUABLE_PILOT_SUPPORT`. Preserve original 36 labels separately. Absolute metrics and matched historic values accompany rankings.
